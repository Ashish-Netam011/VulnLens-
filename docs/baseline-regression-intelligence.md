# Baseline-Aware CI Regression Intelligence (Phase 6D)

This document is the **authoritative** description of VulnLens baseline-aware
regression intelligence: how the CLI classifies findings against a committed
baseline, how the CI gate uses those classifications, and what the security
invariants are.

## 1. What a baseline is

A baseline (`vulnlens.baseline.json` by default, overridable with
`--baseline <file>`) is a **committed, reviewed snapshot of accepted findings**.
It is a **suppression/triage mechanism for CI regression tracking — NOT a
severity-reduction mechanism**.

Baselining a finding means: *"a human has reviewed this exact vulnerability at
this location and accepted it as known, so it should not fail CI again until it
changes."* It never means *"this is now harmless."*

The baseline is **never modified by the scanner or by CI**. It only changes via
explicit, reviewed, human edits to the JSON file. CI must never silently accept
new vulnerabilities by rewriting the baseline.

## 2. The three classifications

Every scan with an active baseline produces three views of the same data:

| Class | Meaning | Fails CI (`--fail-on`) |
|---|---|---|
| **NEW** | Finding exists in the current scan but not in the baseline | Yes, evaluated normally |
| **BASELINED** | Finding exists in both the current scan and the baseline — a known/accepted finding | No (unless severity **escalated**, see §5) |
| **RESOLVED** | Baseline entry that no longer matches any current finding — a previously accepted finding has disappeared | No |

Example:

```text
Security Findings
────────────────────────────────────────────

NEW
  HIGH  hardcoded-secret
        backend/src/config/example.js:42

BASELINED
  HIGH  hardcoded-secret
        backend/src/config/env.js:18

RESOLVED
  HIGH  dangerous-function
        backend/src/legacy/example.js:91
```

- **NEW** drives CI failure. This is the entire point: new vulnerabilities must
  block the pipeline.
- **BASELINED** findings stay **fully visible** — rule, severity, file, line,
  message, evidence — in the table, JSON, and SARIF output. The baseline only
  changes *gating*, never visibility.
- **RESOLVED** findings are reported in the table and JSON summaries as useful
  regression intelligence (e.g. a fix may have landed, or a line may have
  moved). They are **never** current findings, never appear in SARIF results,
  never fail CI, and are never silently deleted from the baseline file.

## 3. How comparison keys work (finding identity)

The baseline comparison key is the same stable identity Phase 6C introduced:

```text
comparisonKey = filePath :: ruleId :: line
```

Generated by `baselineSignature(filePath, ruleId, line)`:

1. `filePath` is normalized: backslashes become `/`, and any leading `/` is
   stripped, so `src\scanner\rules\xss.js`, `src/scanner/rules/xss.js`, and
   `/src/scanner/rules/xss.js` all produce the same key.
2. The key is `filePath::ruleId::line` (e.g. `src/a.js::eval::10`).

This key is **deterministic and stable** across developer machines, CI runs,
repeated scans, baseline generation, and later scans of the same code, because
it depends only on:

- the rule that fired (`ruleId`),
- the normalized relative path of the file,
- the line number.

It deliberately does **not** depend on: generated random IDs, timestamps,
AI-generated descriptions, mutable messages, content hashes, or
machine-specific absolute paths.

> The finding-level `comparisonKey` (e.g. `src/a.js:eval:10:abc123`) used for
> rescan diffing and SARIF fingerprints is a **separate** identity and is not
> changed by the baseline logic.

### Documented trade-off: line is part of the identity

Because `line` is part of the key, a finding whose code **moves to a different
line** no longer matches its baseline entry and is re-classified **NEW**. This is
intentional and fail-safe: drift always re-opens the gate rather than silently
hiding the finding. The old baseline entry is reported as **RESOLVED**.

If a finding changes so much that its key no longer matches, it becomes NEW.
That is the designed behavior.

## 4. How `--fail-on` interacts with the baseline

```text
for each CURRENT finding:

    if finding.status == BASELINED (and not escalated):
        do not count toward --fail-on

    if finding.status == NEW:
        evaluate severity normally

        if severity >= configured threshold:
            FAIL
```

Example: a `--fail-on high` gate with two baselined HIGHs and one NEW HIGH:

```text
Findings:
  HIGH  BASELINED        -> does not fail
  HIGH  BASELINED        -> does not fail
  HIGH  NEW              -> FAIL

Result: FAIL
```

The baseline never implements `HIGH -> LOW`, `HIGH -> ignored`, or
`HIGH -> hidden`. Severity stays authoritative; only the gate input changes.

## 5. Severity escalation policy (security guard)

Baseline entries **may** record the severity that was reviewed:

```json
{ "filePath": "src/a.js", "ruleId": "eval", "line": 10, "severity": "high" }
```

This field is **optional and backward compatible** — the committed Phase 6C
entries do not have it and behave exactly as before.

When an entry records a severity and the current finding at the same key is
**more severe** than what was recorded (e.g. baseline `high`, current
`critical`), the finding is still classified **BASELINED** (identity matched,
severity untouched) but is an **escalation** and is **re-added to the
`--fail-on` gate**. A reviewed baseline must never mask a worse finding at the
same location.

- Entry records `high`, current is `high` → BASELINED, no escalation, gate ok.
- Entry records `high`, current is `critical` → BASELINED + **escalated**, gate fails.
- Entry records `high`, current is `medium` → BASELINED, no escalation (less severe).
- Entry records no severity, current is `critical` → BASELINED, gate ok
  (Phase 6C behavior). Record severities in new baselines to get escalation
  coverage.

Escalations are surfaced in every report: a `baselineEscalated` flag on the
finding (JSON/SARIF), an `ESCALATED` count in the table/JSON baseline summary,
and an explicit stderr note.

## 6. Baseline file format

```json
{
  "version": 1,
  "purpose": "human-readable rationale",
  "entries": [
    { "filePath": "src/a.js", "ruleId": "eval", "line": 10, "severity": "high", "message": "reviewed 2026-09-06" }
  ]
}
```

Required per entry: non-empty string `filePath`, non-empty string `ruleId`, and
a **non-negative integer** `line`. Optional (additive, backward compatible):
`severity` (one of `critical | high | medium | low | informational`) and
`message` (free text).

## 7. Malformed / missing baselines (fail-visible, never silent)

| Situation | Behavior |
|---|---|
| `--baseline file.json` and the file does not exist | **Exit 2** (workflow error) |
| Baseline JSON is malformed (`{ not json`) | **Exit 2** |
| Entry missing `filePath` / `ruleId`, bad `line` (float, negative, non-integer), unknown `severity`, control characters, or over-long fields | **Exit 2** |
| No `--baseline` flag and no `vulnlens.baseline.json` in the working directory | No baseline — scanner behaves exactly like Phase 6C (all findings gate) |
| `--baseline` flag omitted but `vulnlens.baseline.json` exists in the working directory | Auto-discovered and applied |

Malformed baseline data can never bypass the gate: a baseline that cannot be
parsed or validated stops the scan with exit 2 instead of silently scanning
without protection. Baseline content is validated before any classification
happens and is used only for key matching — never for filesystem access.

## 8. Severity is always authoritative

Baseline matching **never mutates** a finding's:

- severity,
- confidence,
- risk,
- vulnerability classification,
- evidence,
- source location,
- rule identity.

Example — the baseline says `high`, the current scan says `critical` at the
same key. The finding stays `severity: critical`, `status: BASELINED`, and
(per §5) re-enters the gate. Only CI gating behavior changes.

## 9. SARIF behavior

SARIF 2.1.0 output retains **all** current findings — NEW and BASELINED alike.
Baseline status is exposed as additive, SARIF-valid result metadata:

```json
"properties": {
  "kind": "code",
  "baselineStatus": "BASELINED",
  "baselineEscalated": true
}
```

No core SARIF fields are corrupted and no findings are removed because they are
baselined. See `docs/sarif-reporting.md`.

## 10. How CI behaves

The GitHub Actions workflow (`.github/workflows/vulnlens.yml`) runs:

```bash
vulnlens scan src --format sarif --output vulnlens.sarif \
  --baseline vulnlens.baseline.json --fail-on "${VULNLENS_FAIL_ON:-high}"
```

Expected policy:

```text
NEW HIGH / NEW CRITICAL               -> fail
BASELINED HIGH / BASELINED CRITICAL   -> do not fail
BASELINED + severity escalated        -> fail
LOW / MEDIUM                          -> follow --fail-on as configured
```

The SARIF file is written before the exit code is derived, so Code Scanning
receives results even when the gate fails. Least-privilege permissions
(`contents: read`, `security-events: write`) and fork-safety are unchanged; no
secrets are introduced. The baseline file is never modified by CI.

## 11. Keeping the baseline honest

A baseline is a security decision, not a configuration detail:

1. **Any NEW finding** at or above the gate threshold fails CI — this is
   correct. Do not weaken it.
2. **Triage** the new finding. Fix genuine vulnerabilities. Only findings that
   are reviewed and accepted belong in the baseline.
3. **Add accepted findings manually** to `vulnlens.baseline.json` with a
   `severity` (so escalations are detected) and a short `message` recording the
   review. Commit the change together with the code review that justifies it.
4. **Do not** bulk-add findings to make CI green. The baseline is metadata for
   regression tracking, not a security exemption from analysis.
5. **RESOLVED entries** (baseline entries with no matching current finding)
   tell you a previously accepted finding disappeared — usually a fix, or a
   line moved. Verify, then optionally remove the stale entry in a reviewed
   edit. The scanner will not do this for you.

## 12. CLI reference

```bash
# Explicit baseline
vulnlens scan ./src --baseline vulnlens.baseline.json --fail-on high

# Auto-discovery (vulnlens.baseline.json in the working directory)
vulnlens scan ./src --fail-on high

# Machine-readable classification (JSON)
vulnlens scan ./src --format json --baseline vulnlens.baseline.json

# SARIF with baselineStatus properties
vulnlens scan ./src --format sarif --output vulnlens.sarif --baseline vulnlens.baseline.json

# No baseline: identical to Phase 6C behavior
vulnlens scan ./src --fail-on high
```

Exit codes (unchanged):

| Code | Meaning |
|---|---|
| `0` | Scan completed; no **NEW** findings meet the failure threshold |
| `1` | Scan completed; **NEW** findings meet the failure threshold |
| `2` | CLI usage/configuration error (incl. missing explicit / malformed baseline) |
| `3` | Scanner or runtime error |

## 13. Review checklist for NEW findings

When a scan reports `NEW` findings, the developer should:

1. Read the finding: rule, severity, file, line, evidence, reason.
2. Confirm whether it is a real vulnerability (use the AI/rule explanation).
3. Fix it if real. If it must be accepted temporarily, add it to the baseline
   **with recorded severity** and a review note — never by auto-accepting.
4. Re-run the scan: the finding should now be `BASELINED`, still fully visible,
   and the gate should pass only if nothing else is NEW at/above the threshold.

## 14. CI runtime immutability (Phase 6E)

In CI, the committed baseline is hashed (SHA-256, exact file contents)
immediately after checkout and re-verified after the scan; any runtime
modification during the job (change, deletion, or replacement by any process)
fails the job. See `docs/ci-cd-github-actions.md` → "Phase 6E" for the exact
steps.

- **Legitimate updates stay possible**: a reviewed, source-controlled baseline
  change is simply the file present at job start — it records a different hash
  and passes. Only *runtime* modification is rejected.
- The hash check is an **additional** integrity layer. It does not replace the
  CLI schema validation (malformed baseline → exit 2) or the NEW /
  BASELINED / RESOLVED classification.
